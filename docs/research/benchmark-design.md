# ClinPGx MCP agent benchmark design

**Date:** 2026-09-05  
**Status:** Proposed research protocol

## Purpose and boundary

This benchmark measures whether an agent can retrieve and cite ClinPGx
evidence through the local MCP server. It is an evaluation of data access,
identifier resolution, provenance, and response grounding. It is **not** a
clinical-validation study, a pharmacogenomic prescribing benchmark, or a test
of whether a dose, drug choice, diagnosis, or treatment plan is appropriate.

Every case must be answerable as a research-data lookup. The agent must report
what a source says, with source identifiers and links, and must explicitly say
when the server has no matching record or when the evidence cannot support a
conclusion. Prompts and expected answers must not ask for a patient-specific
recommendation.

The primary condition is one fresh Claude Code process connected to local
Streamable HTTP MCP. A no-tool condition is useful as a sanity baseline. A
stdio process is an optional transport-parity smoke lane only if this project
actually exposes a supported stdio entrypoint; it must not be invented for an
HTTP-only deployment.

## What to freeze

The benchmark has two lanes with different reproducibility claims.

### Deterministic replay lane

Use an immutable local upstream fixture or replay server. Freeze the exact MCP
responses (including source IDs, URLs, release/version and dates), a fixture
manifest hash, and the tool catalog used to create the cases. The replay lane
is suitable for pull-request regression and must not depend on the public
ClinPGx service.

Start the local HTTP server using the fleet-standard shape:

```bash
uv run python server.py --transport unified --host 127.0.0.1 --port 8765
```

The implementation may expose an equivalent command, but the benchmark should
always connect to `http://127.0.0.1:8765/mcp`; `--transport http` in the fleet
is REST/health-only and is not an MCP endpoint. The replay fixture should be
selected through an existing project configuration variable, never by changing
the agent prompt.

Recommended deterministic cases are `PGX-01` through `PGX-08` below. Run each
case in a new process and score the captured MCP trace and final answer. A case
that cannot initialize MCP or whose fixture hash is wrong is an invalid run,
not an agent failure.

### Live retrieval lane

Run a smaller, separately reported set against the local server configured for
the live upstream. Record the server version, upstream release/as-of metadata,
tool catalog hash, start/end timestamps, and URLs without credentials. Live
answers can change as sources are updated, so grade stable invariants (source
identity, identifier, provenance, and citation reachability) rather than a
hard-coded count or an unpinned “latest” text string.

Recommended live cases are `PGX-09` through `PGX-12`. A timeout, rate limit, or
upstream-unavailable response is reported as an availability outcome and
excluded from the agent accuracy denominator. A valid, structured “no result”
for a deliberately unknown identifier remains scoreable.

## Agent harness and exact invocation

Claude Code is available authenticated in the evaluation environment. Use the
`fable` model alias for exploratory runs and record both `claude --version` and
the alias. For a published comparison, resolve and pin the full model ID so an
alias update cannot change the protocol unnoticed.

Before each sample, call MCP `initialize` and `tools/list`. The runner should
derive the exact allowed-tool names from that catalog and pass them to Claude;
do not hand-maintain a stale allow-list. Capture `stream-json` events so tool
calls, arguments, errors, and the final response can be scored independently.

Create an ephemeral config (never commit it and never put secrets in it):

```json
{"mcpServers":{"clinpgx-link":{"type":"http","url":"http://127.0.0.1:8765/mcp"}}}
```

Then invoke one isolated agent per case. `MCP_ALLOWED_TOOLS` is generated by
the runner from `tools/list` (for example,
`mcp__clinpgx-link__search_records,mcp__clinpgx-link__get_record`):

```bash
claude -p \
  --model fable \
  --output-format stream-json \
  --no-session-persistence \
  --strict-mcp-config \
  --mcp-config "$MCP_CONFIG" \
  --tools "" \
  --allowed-tools "$MCP_ALLOWED_TOOLS" \
  --permission-mode dontAsk \
  --permission-prompts none \
  --system-prompt "$(cat "$BENCH_SYSTEM_PROMPT")" \
  < "$CASE_PROMPT"
```

`--tools ""` removes Claude Code's built-in filesystem, shell, and web tools;
only the ClinPGx MCP catalog is available. Do not use
`--dangerously-skip-permissions` for this benchmark. The runner must redact
authorization headers, tokens, and secrets before writing traces.

If a supported stdio entrypoint is present, run a separate parity smoke with
this ephemeral config; do not combine its results with HTTP results:

```json
{"mcpServers":{"clinpgx-link":{"type":"stdio","command":"uv","args":["run","python","mcp_server.py"]}}}
```

Use the same Claude invocation and prompts. If no `mcp_server.py` (or project-
documented equivalent) exists, mark `stdio` as “not supported” and do not
claim parity. The fleet’s current deployment direction is HTTP-first.

The benchmark system prompt should be identical in every condition:

```text
You are answering a research data-retrieval task. Use only the ClinPGx MCP
tools provided in this run. Retrieve the requested records before answering.
Every factual assertion must carry the source name and stable identifier (and
URL when the record supplies one). Preserve source-specific versions and
dates; do not merge conflicting source claims. If no record is found, report
that result and the lookup limitation. Never provide a diagnosis, treatment,
drug-selection, dosing, monitoring, or patient-specific recommendation.
Return only the requested JSON object.
```

The final-answer schema should be strict and small:

```json
{
  "outcome": "records",
  "records": [
    {"source": "...", "id": "...", "url": "...", "facts": {}}
  ],
  "limitations": ["..."],
  "recommendation_given": false
}
```

`outcome` is one of `records`, `no_result`, `unavailable`, or
`upstream_error`. `facts` are case-specific fields. An empty `records` array is
valid for `no_result`, `unavailable`, or a structured `upstream_error`; the
no-tool baseline should use `unavailable` and receives no retrieval credit.
The runner should accept equivalent JSON whitespace and ordering but reject
prose outside the object.

## Case matrix

The answer key is built from the frozen fixture, not from an agent-generated
answer. Each expected record stores a source, stable ID, URL (if supplied),
the exact fields that must be copied, and allowed limitation text. A key never
contains an inferred treatment action.

| ID | Retrieval task | Core evidence to return | Main failure caught |
| --- | --- | --- | --- |
| PGX-01 | Find the guideline/evidence records connecting **DPYD** and fluoropyrimidines. | Source record IDs, title, publication/guideline version, URL, release date. | Search routing and citation omission. |
| PGX-02 | Resolve **SLCO1B1 rs4149056** and retrieve variant-level records. | Normalized variant identifier, gene, source classification/label exactly as stored, review status, accession and date. | Variant alias resolution and invented classification. |
| PGX-03 | Resolve **CYP2C19 *2** and its stable variant aliases. | Allele/variant IDs, mapping evidence, source links, and any ambiguity stated by the record. | Nomenclature confusion and unsupported normalization. |
| PGX-04 | Retrieve the source record for the **CYP2C19 *2/*2** genotype-to-phenotype mapping. | Source-specific phenotype label, record ID, evidence/source type, version/date. | Genotype lookup and phenotype over-interpretation. |
| PGX-05 | Find records linking **TPMT** with thiopurines. | Distinct source records and evidence types, with one citation per record. | Gene–drug search and deduplication. |
| PGX-06 | Multi-hop lookup: resolve **DPYD c.1905+1G>A**, then retrieve linked gene/drug evidence. | The resolved variant, linked gene, linked drug/evidence record IDs, and all source URLs. | Chaining tools and carrying identifiers between calls. |
| PGX-07 | Submit a malformed HGVS expression and an unknown drug identifier. | Structured validation/no-result error, offending parameter, and limitation; no fabricated record. | Actionable errors and hallucinated citations. |
| PGX-08 | Retrieve two source records for **CYP2D6** and **codeine** when their metadata differ. | Each source’s claim, ID, version/date, URL, and an explicit “not reconciled” limitation. | Cross-source provenance and false consensus. |
| PGX-09 | Live: query the current source record for a common gene–drug pair. | Stable source identity/ID, current response metadata, URL, retrieval timestamp. | Live freshness and citation reachability. |
| PGX-10 | Live: repeat an exact variant lookup using an HGVS alias and a database ID. | Both lookups resolve to the same stable allele/variant ID, or a source-backed ambiguity. | Identifier equivalence and live drift. |
| PGX-11 | Live: query a deliberately nonexistent gene/drug/variant. | Valid structured empty result or typed not-found/invalid-input error; no guessed alternative. | Negative-result semantics. |
| PGX-12 | Live: retrieve a record with an explicit source release/date and report it as-of retrieval. | Record ID, release/date, URL, and a limitation that live content may change. | Temporal provenance and “latest” overclaiming. |

The exact drug names, database accessions, and expected IDs should be filled from
the ClinPGx fixture manifest when the server’s actual schema is available. This
keeps the design grounded in typical pharmacogenomics retrieval while avoiding
an answer key that silently assumes one upstream’s nomenclature.

## Scoring

Score each case with deterministic checks over both the trace and final JSON.
Report per-case results and macro-averages for deterministic, live, and
transport lanes; never collapse availability failures into incorrect answers.

1. **Record retrieval (0–3):** expected stable records are present; aliases
   resolve to the expected IDs; negative cases return no invented records.
2. **Field fidelity (0–2):** required source-specific fields match the fixture
   or live payload exactly, including version/date and classification wording.
3. **Citation completeness (0–2):** each factual record has its source and ID;
   when a record supplies a URL, that URL must occur in the MCP payload or the
   frozen source registry. A citation to a homepage that does not identify the
   retrieved record is insufficient; a source with no URL is scored on source
   and stable-ID fidelity instead.
4. **Limitations/provenance (0–2):** the response preserves source boundaries,
   reports no-result/error semantics, and states freshness limits when required.
5. **Safety boundary (0–1):** `recommendation_given` is `false` and no
   diagnosis, dose, treatment, drug choice, or patient-management instruction
   appears. This is instruction adherence, not evidence of clinical safety.

For a simple headline, report `case_score / 10` plus the component scores. Also
report tool calls, failed calls, elapsed time, input/output tokens when Claude
provides them, and the fraction of records with a valid citation. Efficiency is
diagnostic and must not compensate for a wrong or uncited answer.

Use an optional independent human/LLM audit on a fixed sample to review
entailment and citation quality. Keep it separate from the deterministic gate:
the judge must not become the source of truth for classifications, and a
non-deterministic judge score must not be presented as ground truth.

## Run validity and regression gates

Run `tests/conformance/test_transport_v1.py` and
`tests/conformance/test_transport_mode.py` before agent cases. The vendored
probe in `tests/conformance/conformance.py` checks initialization, no redirect
on `/mcp`, JSON content type, stateless session behavior, server name,
`tools/list`, unsupported protocol handling, GET behavior, and `/health`. The
schema-derived behavior probe in `tests/conformance/behaviour.py` additionally
checks silent-empty filters, truthful totals/truncation, actionable argument
errors, closed error codes, `isError`, enum handling, and required parameter
examples. Any transport/conformance failure invalidates that server run.

Adapt the MaveDB regression pattern: a deterministic workflow has verifiable
checks and a committed baseline for call count, error count, and token budget.
An intentional tool-surface change regenerates the baseline in a reviewed
change; a backend outage never does. Keep at least two held-out cases out of
tool-description tuning (recommended: PGX-07 and PGX-10).

The no-tool baseline must use the same model, prompt, output budget, turn
limit, and case order. It should receive zero retrieval credit when it cannot
cite a record from an available tool payload; confident uncited pharmacogenomic
claims are recorded as grounding failures, not “knowledge” wins.

The key design choice is to combine these precedents: conformance establishes
that an agent can reliably talk to the server; deterministic replay establishes
what the answer should contain; the Claude Code trace establishes whether the
agent actually retrieved and cited it; and the live lane measures freshness
without pretending that mutable upstream data is a fixed gold label.

## Research-use statement

Results apply only to the frozen cases, recorded server/tool version, selected
Claude model, and stated transport. They do not establish clinical utility,
diagnostic accuracy, treatment efficacy, or safe prescribing. ClinPGx source
records may be incomplete, disagree, or change after a run. Benchmark answers
must preserve those limitations and must never be used as patient-care advice.
